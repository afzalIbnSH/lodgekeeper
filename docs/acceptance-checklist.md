# Lodgekeeper acceptance checklist

Use the [plan's progress and handoff rules](implementation-plan.md#milestones-and-progress) to record evidence and complete milestones. Every item starts unverified; check its box only when all parts pass. Use fictional guests and ID images throughout.

Reuse the financial test cases and expected amounts when testing forms and reports. These checks verify that inputs are handled correctly and the expected information appears on screen and in print.

## Accounts and access

- [ ] **A1** Provisioning creates a UUID user with a generated username/password and an encoded Argon2id hash. Plaintext credentials do not enter the database, routine logs, or source control. Username trim/case normalization works consistently for creation and login; normalized duplicates are rejected.
- [ ] **A2** Login/logout work; wrong credentials fail; anonymous and disabled users cannot access bookings, rent/deposit transaction recording, reports, rate edits, uploads, or ID reads. Disabling an already logged-in user removes their access on subsequent requests.
- [ ] **A3** Changing requests require CSRF protection; redirects cannot send users to an untrusted destination; repeated failed logins are bounded across application processes. Production cookies and HTTPS settings pass the configured deployment checks.
- [ ] **A4** A fresh environment can install dependencies, start PostgreSQL and Garage through Docker Compose, initialize Garage's local bucket/access credentials, migrate, provision a user, and run CI checks from the README. CI starts isolated PostgreSQL and Garage instances using the same pinned service versions and needs no Cloudflare credentials. Readiness checks pass for both services. Local/CI PostgreSQL matches the documented production target major version and supports the required extensions, including `btree_gist`; verify the actual deployed environment under O1. No registration or staff role-management interface exists.

## Database and provisioning

- [ ] **D1** All six business tables match the documented fields, foreign keys, UUIDs, timestamps, and indexes. Database checks reject blank required text, unsupported ID types, invalid conditional fields, impossible timestamp ordering, and invalid amounts even when the ORM/forms are bypassed.
- [ ] **D2** Non-finite amounts (`NaN` and infinities) and timestamps are rejected by PostgreSQL. Creation/update timestamp handling is consistent on supported write paths. Unit type names, unit labels, and usernames enforce their documented normalized uniqueness.
- [ ] **D3** Both named exclusion constraints exist with their exact predicates and inclusive `[]` boundaries; `btree_gist` is installed before them. The actual occupancy range has an unbounded end until checkout. Test migrations on an empty database and through subsequent upgrades.
- [ ] **D4** Booking numbers are unique under concurrent creation and remain valid after restoring a backup. Referenced users, unit types, units, and bookings cannot be deleted.
- [ ] **D5** Unit/type seeds are repeatable, support text labels such as `A-01`, and preserve staff-edited rates. Inactive inventory cannot receive new allocations. Existing historical bookings and reservations remain accessible after inventory is retired.
- [ ] **D6** `booking_transactions` accepts exactly `PAYMENT`, `REFUND`, `DEPOSIT_RECEIVED`, and `DEPOSIT_RETURNED`, defaults to `PAYMENT`, and requires a positive finite amount and finite `transacted_at`. Only `REFUND` requires a nonblank reason; a deposit return can omit one. Each entry references its recording user and booking, with no links between outgoing and individual incoming entries. Direct writes under the runtime role can insert valid entries but cannot update, delete, or truncate them. That role does not own the table or inherit migration privileges; both shared record timestamps remain unchanged after insertion. No required-deposit or stored deposit-balance field is introduced.

## Money and transactions

- [ ] **F1** The shared calculation produces `0.00 = 0.00 + 0.00 + 0.00`, `250.00 = 238.08 + 5.96 + 5.96`, and `600.00 = 571.42 + 14.29 + 14.29`. The ₹250 case exercises upward rounding of half a paisa per tax. No binary float enters calculations or storage.
- [ ] **F2** Representative allowed totals and a broad range of paise inputs preserve `total = base + cgst + sgst` exactly, equal taxes, nonnegative base, and each tax at least 2.5% of the final base. Both application validation and direct database writes accept zero or totals of at least ₹250, and reject negative totals and `0.01` through `249.99`. Reject excessive input precision, overflow, and non-finite inputs with usable errors. Exercise the numeric upper boundary and daily-rate multiplication overflow. A free stay creates no zero-value payment row. The ₹250 minimum does not apply to individual payments, refunds, or deposits.
- [ ] **F3** Initial total equals the selected daily default times booked days unless overridden. Saved daily rate, unit/type labels, total, and taxes remain unchanged when current inventory rates or labels change.
- [ ] **F4** Editing the booking's own total recomputes only that booking's taxes with the shared algorithm. The database rejects inconsistent totals or negative components; browser requests cannot supply trusted tax or snapshot values.
- [ ] **F5** Services attribute each entry to the authenticated user. History queries return correct types, reasons, recording users, and event times distinct from record creation for zero, one, and multiple entries of all four types. Separate rent/deposit totals and balances are derived correctly, with zero for empty sums. A rent payment of ₹800 followed by rent refunds of ₹200 and ₹600 produces three unchanged entries and zero net rent paid. History uses deterministic ordering when event times coincide.
- [ ] **F6** Repeating a submission for any of the four transaction types, including concurrently, records one entry. A combined rent/deposit collection retry reuses both original rows. Retrying a successful full refund or deposit return returns the original result even though the relevant balance is now zero. Reusing its token with changed values is rejected. Two deliberately separate equal transactions both persist when their applicable limit permits them.
- [ ] **F7** Cancelling a reservation with rent payments or deposits preserves the booking and every entry, without automatically recording money returned. Checkout alone also leaves the deposit held unchanged. Later rent payments can settle a checked-out stay; partial/full rent refunds and deposit returns remain possible after checkout or cancellation. Booking details stay read-only in those states, and no service can edit or delete existing transaction rows in any state.
- [ ] **F8** Rent refunds cannot exceed current net rent paid, excluding all deposits. With ₹800 net rent paid, two independent concurrent ₹600 rent-refund attempts cannot both commit; the remaining ₹200 can then be refunded. Refunds with no net rent payments are rejected even if a deposit is held. A single ₹800 refund against rent payments of ₹600 and ₹400 is allowed and leaves ₹200 net rent paid. All insertion paths use the parent booking lock, and a failed validation/database transaction leaves prior records and balances intact.
- [ ] **F9** Recording any money movement alone leaves saved rent, taxes, and checkout timestamps unchanged. With ₹1,000 rent and ₹1,200 explicitly recorded as rent payment, a ₹200 rent refund clears the rent credit and leaves zero rent pending. With ₹1,000 rent and ₹1,000 rent paid, a ₹200 rent refund leaves ₹200 rent pending unless a separate permitted rent change is made. No automatic rent adjustment, deposit classification, or money return is inferred from a balance.
- [ ] **F10** The optional deposit received input defaults to ₹0, and blank/zero creates no deposit entry. A positive amount creates `DEPOSIT_RECEIVED`; reject negative, non-finite, excessive-precision, and out-of-range values. A ₹0.01 deposit is valid because deposits do not use the rent GST calculation. Changing rent/days does not change the deposit input, and revisiting or editing a saved booking does not duplicate earlier deposit receipts. A combined rent/deposit collection commits both entries or neither.
- [ ] **F11** For ₹800 rent, collecting ₹800 rent payment plus ₹200 deposit creates two entries and shows zero rent pending with ₹200 deposit held. Returning ₹200 creates `DEPOSIT_RETURNED`, clears the deposit, and leaves rent paid/pending and GST unchanged. With only ₹600 rent paid and ₹200 deposit held, pending rent remains ₹200. A rent refund does not reduce deposit held, and a deposit return does not reduce net rent paid.
- [ ] **F12** Deposit returns cannot exceed deposit held, even when rent payments are available. With ₹200 held, two independent concurrent ₹150 return attempts cannot both commit; the remaining ₹50 can then be returned. A deposit collected in installments can be returned in one or several entries. A rent refund and a deposit return can both succeed when each has sufficient balance, without spending the other balance.

## Booking lifecycle and concurrency

- [ ] **B1** A future reservation requires a specific unit, caller name and phone, scheduled arrival, booked days, and expected checkout. The caller can differ from every occupant. It can be created without guest records, shared address, purpose, or ID uploads.
- [ ] **B2** A walk-in or reservation check-in requires at least one complete guest, each guest's ID image, one shared address, and purpose. Multiple guests are supported without reusable profiles or additional address fields. An incomplete save leaves no partial check-in, initial rent payment, or deposit receipt.
- [ ] **B3** Default checkout is 24 elapsed hours times booked days after the applicable arrival; explicit checkout and total overrides persist. Reservation check-in retains scheduled arrival and explicitly submits its final expected checkout. Expected checkout must be after both supplied arrival times.
- [ ] **B4** Cancelling an unarrived reservation stores cancellation time and immediately frees its interval. It cannot be checked in afterward. Cancellation is rejected once actual check-in exists. Competing cancellation/check-in attempts leave one valid final state.
- [ ] **B5** Two overlapping reservation saves for the same unit, on independent database connections, cannot both commit. Nonoverlapping intervals and overlapping bookings for different units can commit. A conflicting amendment is also rejected.
- [ ] **B6** Inclusive boundaries are enforced: one booking's checkout and another's check-in cannot share a timestamp. A strictly later arrival can succeed when no other conflict exists. Apply this to expected allocations and actual history.
- [ ] **B7** A checked-in guest remains occupied after scheduled checkout. A future reservation strictly after scheduled checkout is allowed, but actual check-in of the next guest is blocked until the occupant's actual departure.
- [ ] **B8** Late actual checkout can extend into an unarrived reservation without failing the expected-overlap constraint. The next actual check-in must be strictly after the recorded actual departure. Two actual stays can never overlap, including backdated completed stays.
- [ ] **B9** Early reservation check-in uses actual arrival for the allocation constraint and rejects overlap with another reserved/occupied allocation. Neither the form nor a service caller can bypass the constraint with stale availability data.
- [ ] **B10** Future actual arrival, actual departure, and cancellation are rejected. A backdated completed stay supplies arrival and departure together and is checked against historical actual stays. Departure before or equal to arrival is rejected.
- [ ] **B11** Checkout, amendments, guest writes at check-in, all four financial-entry types, and repeated submissions revalidate state under concurrent access. Forms and services enforce the PRD's edit limits for each state, including the fixed unit and snapshots. Failed database transactions preserve previous bookings, guests, rent/deposit entries, and snapshots; known conflicts return useful errors, not unexplained server failures.

## Guest ID storage

- [ ] **I1** The private R2 bucket is inaccessible anonymously. Authenticated ID views enforce access checks; temporary read URLs expire. Default screens/receipts do not expose private object keys or unintended ID data in markup or logs.
- [ ] **I2** Each guest can capture or choose an image on the target phone/browser. Validate file content, format, size, and decoded dimensions; disguised files, oversized images, and arbitrary client-supplied object keys are rejected. Every checked-in guest has a server-verified stored image.
- [ ] **I3** Failure on the second guest's upload leaves the reservation unchecked-in. A booking conflict after successful uploads retains those objects and allows a safe retry without silently duplicating the booking, initial rent payment, or deposit receipt.
- [ ] **I4** Images are never overwritten or deleted by booking cancellation, amendments, failed saves, orphan cleanup, or database-export retention. ID retention protection is exercised against a test object; already-uploaded unlinked images remain identifiable for recovery.
- [ ] **I5** ID requests and sensitive pages are not publicly cached. Errors and routine logs omit guest document data, file contents, credentials, and signed access URLs. Several phone-photo uploads fit within the configured app memory and request limits.
- [ ] **I6** The same `django-storages` S3 backend and application upload/read code target Garage locally/in CI and private R2 in production using only endpoint, bucket, region, and credential settings. Upload/read and retained-upload retry integration tests pass against Garage with fictional images and no Cloudflare access; local uploads remain on the development machine. Record separate actual-R2 evidence for permissions, private access, signed URL expiry, and retention under I1 and I4; Garage or fake-storage results do not satisfy those live checks.

## Staff interface

- [ ] **U1** Occupied units sort by expected checkout ascending initially and can sort descending. Overdue stays remain occupied and visibly distinguishable. Planned interval availability and immediate check-in availability agree with final server validation.
- [ ] **U2** Staff can create/amend/cancel a reservation, check in a walk-in or reservation with multiple guests, override total/expected checkout, record installments through all four transaction forms, and record actual checkout through the browser. Exercise F3–F4 and F10 through the collection forms: editable rent prefill, separate actual-payment/deposit inputs, and the documented defaults and validation. Return forms show the applicable available balance and enforce D6's reason rule. A submitted `created_by_user_id` cannot override authenticated attribution.
- [ ] **U3** Booking number lookup and reservation/stay lists lead to full saved details, including cancelled bookings. Display F5's typed history and totals, F9's rent credit, and F11's separate rent/deposit balances; posted entries have no edit/delete controls. Checkout shows deposit held and an input for an actual return. Later payment/return actions from F7 remain reachable, and any deposit remainder stays visible. Show one shared address and label scheduled versus actual times clearly.
- [ ] **U4** Staff can edit a type's default rate; they cannot create units/types or edit snapshots through those forms. A new booking uses the new rate while an existing booking retains its old agreement.
- [ ] **U5** Main workflows work on lodge desktop and phone sizes with clear labels, keyboard access, understandable errors, and submit feedback. Essential validation works when JavaScript is bypassed. Run F6's retry cases and F8/F12's competing-return cases through the forms. Check redirects after success and useful errors with refreshed choices/totals after a conflict. Invalid or stale submissions preserve entered values and reusable successful uploads; server validation still enforces the financial rules.

## Receipts and ledger

- [ ] **R1** A receipt shows shared property details, reference, saved unit/type, all guest names, shared address and purpose, stay times, and agreed rent/taxes. Using F5/F9/F11 fixtures, verify the rendered history includes all four transaction types and every total/balance from the [transaction contract](implementation-plan.md#transactions-and-booking-edits), with rent clearly separate from deposits. Reprint after F7's later collections/returns and check the updated output. By default, ID type, number, and picture are absent from the response; an explicit authenticated inclusion option adds them and their protected images.
- [ ] **R2** Ledger selection uses actual checkout in `Asia/Kolkata`: a stay arriving on 31 October and checking out on 1 November belongs wholly to November, regardless of payment dates. An open stay with an October expected checkout is absent from October's ledger until an actual October checkout is recorded.
- [ ] **R3** Actual checkout at 1 November 00:00 local time is included in November; checkout at 1 December 00:00 is excluded. Arbitrary inclusive date ranges use the same local-date conversion. Invalid/reversed dates return errors, and empty ranges produce a printable zero-total ledger.
- [ ] **R4** Each checked-out booking with nonzero agreed rent contributes one row from its saved unit label/base/CGST/SGST; free stays are excluded. Multiple guests and transactions do not duplicate rows; multiple stays in one unit remain distinct. Unpaid stays are included, cancelled reservations with retained/returned money are excluded, and later rate changes do not affect totals. A later rent payment settling a checked-out stay, rent refund, or deposit return, including in another month, changes the appropriate receipt balance without changing saved rent/taxes or ledger membership/values. Deposits never increase or decrease the ledger amounts.
- [ ] **R5** Receipts and ledgers print legibly with fictional data, including multipage tables and optional ID pictures. Ledger columns match Unit / Rent / CGST / SGST with exact totals. Navigation is absent from print, and missing requested images are reported visibly.

## Deployment and operation

- [ ] **O1** The intended Render environment starts with production settings, correct Singapore placement, managed HTTPS, private R2 access, bounded database connections, and health/error checks. Its actual PostgreSQL major version and required extensions match local and CI configuration, with comparison evidence recorded. It uses the restricted runtime database role, with separate migration credentials. Real property configuration and unit data are correct. No secrets are committed or exposed by diagnostics.
- [ ] **O2** Daily database exports reach protected R2 storage, failures are visible, and export retention does not affect IDs. The documented recovery process restores a fresh database, including constraints, booking-number sequence state, all four transaction types/attribution, and the required roles/grants. Verify separate rent/deposit totals and balances and runtime restrictions after restore; restored bookings can load their retained ID images.
- [ ] **O3** The runbook covers setup, provisioning/reset, units, deployment/migrations, backup recovery, rollback limits, dependency updates, and storage growth. Fresh install, upgrade, migration-drift, test, and deployment checks all pass.
- [ ] **O4** Simultaneous booking and report activity is measured using at least five years of representative synthetic data on the intended small database. Record memory and query/page timings, assess the plan's proposed responsiveness targets, and test access from the lodge before launch.
- [ ] **O5** A client walkthrough completes a reservation with a deposit collected and returned, a multi-guest walk-in with no deposit, installment rent payments, cancellation with installment rent refunds, actual checkout, receipt, and checkout-based monthly ledger. Show retained transaction history and separate rent/deposit balances. Phone capture and the lodge's printer work. A recent backup and successful restore rehearsal are recorded before live use.
